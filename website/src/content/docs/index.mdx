## Start by listing your stacks

The first successful read lists the Stacks your Core identity can see. It changes nothing in Komodo.

```text title="First read: list your stacks"
List the stacks I can access in Komodo and show their current status.
Use list_stacks and do not change anything.
```

<Steps>
1. **Build and connect.** [Build the executable](/getting-started/stdio/) with the pinned Rust toolchain, then [add it to your MCP client](/getting-started/clients/) with your Core address, API key, and secret.

2. **Approve one read.** Your client should propose `list_stacks`. It is read-only and returns at most 30 Stacks per page by default.

3. **Review the answer.** Each Stack has a stable ID, its Core state such as `running`, `stopped`, or `unknown`, and its active Server or Swarm target (`null` when unassigned). Follow `next_page` until `has_more` is false; an empty list is valid when the identity can read no Stacks.
</Steps>

## Diagnose a failed stack without changing it

When a Stack looks unhealthy, keep the investigation read-only and let the server report what it could and could not observe.

```text title="Read-only diagnosis prompt"
One of my Komodo stacks looks unhealthy. Find it with list_stacks,
confirm its exact ID with get_stack, then run stack_diagnose on that ID.
Report the outcome, the affected services, and any evidence gaps.
Do not deploy, restart, or change anything.
```

<Steps>
1. **Discover the visible Stack.** `list_stacks` (or `fleet_health` across the fleet) shows only resources your identity can read.

2. **Resolve its exact identity.** `get_stack` accepts an exact, case-sensitive name or a 24-character ID. Ambiguous or incomplete name resolution fails safely and asks you to retry by ID.

3. **Inspect the evidence.** `stack_diagnose` combines inventory, service state, recent updates and alerts, and one bounded log tail in at most seven Core reads. It returns `healthy`, `unhealthy`, or `inconclusive` with supporting IDs.

4. **Read the gaps honestly.** A denied, timed-out, oversized, or unavailable source becomes an explicit gap while other evidence remains. Summaries can lag Docker, and correlated history is evidence, not proof of cause. Follow up with `get_update` or `get_stack_logs` if you need more.
</Steps>

[Read the diagnosis bounds and evidence model](/docs/diagnostics/#stack-diagnosis).

## Know when to use it

Choose komodo-mcp when you run your own Komodo Core and want an MCP client to inspect it or make approved changes under that identity's permissions. A source build from `main` runs as a local stdio process or a persistent service with [authenticated Streamable HTTP](/reference/configuration/#authenticated-streamable-http).
