komodo-mcp gives an MCP client, and the model behind it, access to Komodo Core as one identity. Its job is to make that access explicit and bounded. It does not replace Core's permissions or your client's approval prompts.

## Credentials

- `KOMODO_API_KEY` and `KOMODO_API_SECRET` are read from the process environment once at startup. The executable does not read `.env` files or any configuration file.
- They are sent only to the configured `KOMODO_ADDRESS`. Automatic redirects are disabled so credentials cannot follow a redirect to another host. Normal TLS certificate verification stays enabled.
- Configuration and client Debug output show `[redacted]`. Log events, error text, and tool output are redacted for the configured credentials, including verbose dependency traces.
- Wherever your client stores the server's environment is the real secret store. Prefer references to environment variables over literal values in shared files.

## Core data

- Tool results contain Core data visible to the identity: names, IDs, states, targets, bounded history, and redacted log tails. That data passes through your MCP client and its configured model provider. Choose a client and identity accordingly.
- Raw configuration, environment blocks, Compose content, stored files, upstream error bodies, variable secret values, and authentication payloads are not returned. Logs and diagnosis are size-bounded and redacted.
- Lists only show what the identity may read. A missing resource and an invisible one look the same, and inaccessible candidates are never revealed.

Both must allow an action. Grants never add Core permissions, and Core permissions never enable a disabled tool. Your client's approval step is a third, human gate: review the exact target and arguments before approving any tool that is not read-only.

## Transport

With stdio, the MCP client launches a private child process. In HTTP mode, each request requires a configured bearer token. A token identifies the client to MCP. Core authorizes calls using the server's configured service account. Give clients that need different Core permissions separate instances and Core credentials. [HTTP configuration](/reference/configuration/#authenticated-streamable-http)

## Operations and uncertainty

Execution tools are annotated as mutating and non-idempotent, and every change, whether an operation, configuration apply, deletion, prune, or terminal command, is submitted once. A timeout or lost reply means the outcome is uncertain, not that it failed:

1. Do not repeat the call automatically.
2. Observe a known update ID with `wait_for_update` (or `wait_for_resource_sync_update`).
3. Without an ID, use `reconcile_operation`, which lists possible matches with unconfirmed attribution.
4. Verify the workload independently, for example with `stack_diagnose`.

<Aside type="caution" title="Trusted grants">
  Configuration editing can set commands, mounts, environment, and other executable settings. Actions and Procedures can run with Core administrator authority. Enable those grants only for identities and clients you trust with that authority.
</Aside>
