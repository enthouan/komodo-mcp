komodo-mcp acts as exactly one Komodo Core identity: the user that owns the API key and secret you configure. Every call uses that identity's Core permissions. There is no credential fallback, and komodo-mcp never creates users, passwords, or API keys for you.

## Choose the identity

<Steps>
1. **Use an enabled, non-admin identity.** A dedicated user or service user makes the MCP client's access easy to audit and revoke. A disabled user fails the startup probe.

2. **Grant Read where you want visibility.** Inventory and diagnosis need `Read` on the Servers, Stacks, and Deployments being inspected, through a resource grant, a user group, a global or base permission, or transparent mode. Log tools may also need `Logs` where the requested Core API requires it. Admin, Write, Execute, and Create are unnecessary for read-only use.

3. **Create an API key and secret for that identity in Komodo.** Store both in a password manager or your client's secret store. Treat the pair like a password: anyone holding it can act as that user.

4. **Find the Core address.** Use the absolute URL your browser uses for Komodo Core, including any base path, for example `https://komodo.example.test/komodo/`. Point it at the final URL: komodo-mcp does not follow redirects, so credentials never leave the configured Core.
</Steps>

See the [Komodo documentation](https://komo.do/docs/) for creating users, service users, and API keys in your Core version.

## Supply the credentials

All three variables are required. Put them in the environment of the MCP server process, usually through your client's server configuration.

<Aside type="caution" title="Keep credentials out of prompts and repositories">
  Never paste the API key or secret into a chat. Prefer client configuration that references environment variables. If a configuration file must contain the values, keep it user-local with restrictive permissions and out of version control.
</Aside>

## What startup checks

Before it answers MCP initialization, komodo-mcp validates the configuration and sends one authenticated `GetVersion` read. Invalid configuration fails before contacting Core. A rejected key, a disabled user, or an unreachable address exits with a safe stderr diagnostic such as `authentication (GetVersion)` or `unreachable (GetVersion)`. No credential value is ever printed.

## Separate local grants from Core permissions

Core permissions decide what the identity may do. The four optional `KOMODO_ALLOW_*` grants decide which tools this MCP process exposes at all. Both must allow a change: enabling `KOMODO_ALLOW_OPERATE=true` without Core `Execute` on a Stack does not let you deploy it, and Core `Execute` without the local grant does not expose the operation tools. See [Configuration](/reference/configuration/).

## Rotate or revoke

Create the replacement key in Komodo, update the client's environment, restart the MCP server, verify with `list_stacks`, then delete the old key in Komodo. After you delete the key or disable the identity in Komodo, subsequent komodo-mcp requests fail with an `authentication` error.
